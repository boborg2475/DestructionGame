## Snapshot

Design is well developed ([DESIGN.md](DESIGN.md)); implementation has just started. The FPS template is fully stripped and **the project runs**: `Lvl_Sandbox` loads, the flying pawn is the default pawn, and the automation suite is green.

- Git: on `main`.
- **`Content/Maps/Lvl_Sandbox`** — floor, directional light, sky light, sky atmosphere, height fog, PlayerStart. Not World Partition, deliberately: WP writes one file per actor and the sandbox spawns its scenarios from code. Floor is currently the engine template mesh; swapping to `LevelPrototyping/SM_Plane` would give a grid material with visible scale reference.
- `Source/` is clean of template variants. Classes: the module, `GameMode`, `PlayerController`, `CameraManager`, `FlyingPawn`, and `Core/ConnectionLoad` + `Core/ConnectionStrength` + `Core/Connection` + `Core/Structure` + `Core/Profiles`.
- **Test infrastructure works.** Automation tests run headless, verified end to end on a real red → green cycle. Build and run commands are documented in [CLAUDE.md](../CLAUDE.md).
- **`Structure.Fuzz` is a permanent seeded fuzz over the load solver** (`Tests/StructureFuzzTest.cpp`): 12,000 deterministic random structures — 2–8 pieces, tilted as well as axis-aligned normals, areas spanning seven orders of magnitude — checked against universal properties (conservation, finiteness, supported-implies-routed, stranding never travelling downward) and against an independently derived oracle (least-fixed-point support plus Warshall closure for cycles, Jacobi relaxation for the loads, where production uses BFS plus Kahn). **96 ms**, and it prints the failing seed and the whole structure so one case can be reproduced and turned into a named test. It replaces the scratch fuzz harness that was rebuilt from scratch every review round: **run it rather than rebuilding it.**
- **Five core systems are in**, all test-driven. 27 tests, all green.
  - `Core/ConnectionLoad` — resolves a force into compression / tension / shear relative to a connection's interface plane, with the normal-orientation convention pinned down by the Newton's-third-law invariant.
  - `Core/ConnectionStrength` — compares a load against directional strengths in MPa and returns a utilisation ratio (>1 = the joint gives). Shear capacity follows Mohr-Coulomb, growing with compression, so a wall sheds shear resistance as the load above it is removed. Carries `ForceUnitsPerMPaSqCm`, the single SI↔Unreal conversion boundary.
  - `Core/Connection` — `FConnection`, the joint itself: two piece handles, an interface normal, an area and a strength profile, so a caller supplies only a force. Composes the two above and returns the utilisation. Giving **latches** — the breaking call reports the ratio that broke it (>1), every call after it returns 0, because a joint that has given is out of the structure and carries nothing. Phase 2's redistribution depends on that zero.
  - `Core/Profiles` — the shared, real-world-calibrated data. `ConnectionProfiles` carries `GeneralPurposeMortar`, `LimeMortar`, `DryStone`, `Nail`, `Screw`, `Bolt` and a `TestFixture`-classified `Unbreakable`; `MaterialProfiles` carries `StructuralConcrete` (the C30/37 calibration baseline) and `ClayBrick`, each with a density, its own directional strengths and a declared-but-unused `BondFactor`. **Every value carries a citation comment** naming the code or table it came from (EN 1992-1-1, EN 1996-1-1, BS EN 998-2, BS EN 459-1, EN 1995-1-1, EN 338). Each profile row carries an `EConnectionProfileClass`, which is what makes the physical invariants machine-checkable per kind of joint and makes an unbreakable fixture recognisable rather than merely commented. **Adding a profile is adding a row** — the well-formedness sweep in `Profiles.ConnectionInvariants` picks it up for free. The three older test files now read these instead of declaring private copies.
  - `Core/Structure` — `FStructure`, the graph that owns pieces and connections (**phases 2a and 2b: load computation, grounding, breaking and cascade**). Support is **two-tiered** per DESIGN.md §3: a connection's interface normal, turned to point at the piece being asked about, makes it a **bed joint** beneath (substantially vertical, `|Z| > cos 45°`, pointing up at the piece — it bears), a bed joint **above** (points down — bears nothing, that is something resting on this piece), or a **head joint** (anything else). A piece's supports are its bed joints beneath, and *only* a piece with none falls back to its head joints. Everything downstream is computed over that **support relation**, not over raw connectivity: reachability is a breadth-first walk from the grounded pieces over "who rests on me", and accumulation runs in a topological order of the same relation (Kahn — distance to the ground is *not* a valid order, since a spanning brick and the brick on it are equidistant and the second loads the first). Load splits weighted by interface area, **across only those supports that themselves reach the ground** — a share given to a falling piece never arrives, and leaves the joint actually carrying the load reporting a fraction of it. Pieces in an unroutable knot (a cycle: a course spanning a two-brick gap, each brick falling back to its neighbours' head joints) are **reported unsupported**, so `IsPieceSupported` and `GetConnectionForce` agree rather than contradicting each other silently; it is not a claim the cycle was solved. **Only the pieces caught in the knot**, identified by their own load coming back round to them (`LoadReturnsToPiece`) rather than by the Kahn pass failing to order them — the ordering runs top-down, so un-orderability is a strictly larger set that reaches down to the foundations. Pieces beneath a knot keep their support and carry everything except the unroutable contribution. Those two rules feed each other — stranding changes who reaches the ground, which changes who may take a share, so a piece resting only on the knot loses its own support — so `SolveLoads` iterates to a fixpoint, stranding at least one more piece per pass and therefore running at most `NumPieces + 1` passes. The force handed to a joint is vertical, and **signed by which end is being held up** — `-magnitude` when the loaded piece is `PieceB`, `+magnitude` when it is `PieceA`, per `ConnectionLoad.h`'s convention that the force belongs to `PieceB`; `FConnection` then resolves it as compression on a bed joint and shear on a head joint. Solving is **non-destructive**: it never calls `ApplyForce`, so it can be re-run and nothing latches. `AddPiece` / `AddConnection` validate at the door and reject rather than store. **`SolveAndBreak` is the deliberate breaking step** (DESIGN.md §3, "How a structure comes apart"): solve, break *every* joint over its own capacity in the same pass, stamp each with that pass number, re-solve so the share moves onto the neighbours, repeat until a pass breaks nothing — which is the last pass and is not counted. **A joint that has given leaves the support relation entirely**, filtered once at the top of the tier decision in `SolveLoads` so it drops out of the tier, the reachability walk, the load paths and the split together; a piece whose only bed joint has gone therefore falls back to its head joints rather than being reported as falling with an intact joint reading zero. The pass stamp lives in `ConnectionBreakPass`, grown by `AddConnection` and never cleared — the latch on `FConnection` records only *whether* a joint gave, and the stamp is the only record of *when*, which is what phase 5 plays back. **Two things about the break sweep are load-bearing and both were confirmed by mutation**: it holds connections **by reference** (a by-value loop latches temporaries and reports a structure that never breaks), and it **skips already-given joints** — without the skip, `HasGiven` re-reports every old break as new, so the stamp is rewritten and the cascade never terminates (the mutation hangs the suite rather than failing it).
- **`Content/` is clean.** Template strip finished: 22 files remain, all of them in use — the 6 Enhanced Input assets the pawn and controller hard-reference by path, and the `LevelPrototyping` primitives and grid materials (`SM_Plane`, `SM_Cube`, `SM_Ramp`, …) that the sandbox level and brick scenarios will be built from.
- **The world-free half of the MVP is done.** Structures compute their loads, decide what gives, and come apart in a recorded order, all without a world or a ticking solver. Everything remaining on the MVP list needs a world: the harness, the brick actor, scenarios, visualisation, integration tests.

## Conventions and gotchas

**Don't hard-reference content from C++ without checking it exists.** `FlyingPawn` and `PlayerController` both resolve Input assets by path in their constructors via `ConstructorHelpers::FObjectFinder`. That pattern makes content deletion silently dangerous — it fails at construction, not at compile time. Worth a helper or a startup assert if this spreads.

**Automation runs exit 0 even when tests fail**, and results never reach stdout. Always read `Saved/Logs/DestructionGame.log`. See [CLAUDE.md](../CLAUDE.md).

**An anonymous namespace is private to a TRANSLATION UNIT, not to a file — and this applies to every `.cpp` in the module, production as much as tests.** A unity build merges many files into one TU, at which point every anonymous namespace in the blob is the *same* namespace. Two file-local names that collide are then a hard compile error, and it does not matter that the files never refer to each other.

  Confirmed on this toolchain (MSVC 14.44.35207, `/std:c++20`) by hand-building a blob — a scratch `.cpp` that `#include`s two others — and it is worth knowing that trick, because **UBT will not currently produce the condition for you**: `MinGameModuleSourceFilesForUnityBuild` defaults to **32** and this module has **17** `.cpp` files, so it compiles non-unity regardless of git status, `-StressTestUnity`, or what is committed. The log line *"Using 'git status' to determine working set for adaptive non-unity build"* is the working-set provider announcing itself and is **not** evidence that adaptive unity is what is keeping files apart. **The landmine arms itself at 32 source files**, and at one test file per behaviour this project will get there.

  Two places it has already been dodged, both worth copying:
  - **Test files use distinct named support namespaces** — `StructureTestSupport`, `ConnectionTestSupport`, `ConnectionStrengthTestSupport`, `StructureFuzzSupport`, `ProfileLibraryTestSupport` — with the `using namespace` **inside each `RunTest` body** rather than at file scope. A file-scope using-directive would leak those names into every TU after it in a blob and reintroduce the ambiguity by another route.
  - **Production file-local arrays are named for their contents**, not `Library`: `ConnectionProfileLibrary` and `MaterialProfileLibrary`. They previously collided (`error C2371: 'DestructionProfiles::`anonymous-namespace'::Library': redefinition; different basic types`). Note a shared named namespace would **not** have fixed it — the clash is on the name.

  One straggler: `StructureFuzzTest.cpp` still builds its unbreakable joint from an inline `FConnectionStrength{ 1.0e9, 1.0e9, 1.0e9, 0.0 }` rather than `DestructionProfiles::Unbreakable`. Harmless — it is a local literal, not a second copy of a named constant — but it is the last inline strength profile in the suite.

**`ConnectionStrength.ShearCap`'s compressions are literals chosen against mortar's current numbers.** The test feeds 3.0 and 4.0 MPa of compression, which have to sit in a window to measure what the test is named for: **above** where the cap bites (`(MaxShear - Cohesion) / mu`, currently `(1.3 - 0.2) / 0.6` = 1.83 MPa — below it, friction is uncapped and the test measures plain Mohr-Coulomb) and **far enough below** mortar's compressive limit that shear still governs (at 4.0 MPa compression is at 0.4 against shear's 0.77). The ceiling itself is read from the profile, so it tracks a retune; these two inputs do not. Low risk — the assertions fail loudly rather than silently if the window moves — but a retune that raised the cap past ~2.6 MPa or dropped compressive strength toward 5 MPa would quietly change what is under test. Fix by deriving the compressions from the bite point, with a fixture precondition asserting the window, as `Profiles.DryStoneCarriesLoadByFrictionAlone` does.

**An invariant asserted over fixtures that all share a hidden property is not an invariant.** "A gravity load path never pulls a joint open" was green across the whole suite — because every interface normal in every fixture was axis-aligned. Tilt one and 337 of 6,000 fuzzed structures produce tension. The same shape caught the stranding bug: ground-reaction conservation could not see it, because over-stranding removes a piece's weight from *both* sides of the equation. When an invariant has never failed, check whether it *can*.

**Reviews cost 7–19 minutes and have earned it, but scale the depth to the risk.** Every round on the load solver found a real defect, and the two that mattered most were found by transcribing the solver and fuzzing it against an independent oracle rather than by reading. That is worth it for topological code with silent failure modes. It is not worth it for a table of material constants. Don't ask a review to re-verify findings already closed in an earlier round — that was 20–30% of the cost and proved nothing new. **That fuzz is now `Structure.Fuzz` in the suite** — extend its tables or its case count rather than rebuilding a scratch harness, and if the review needs a property the fuzz does not assert, add it there so the next round inherits it.

**A green-on-arrival test is indistinguishable from one that asserts nothing until you mutate production.** `Structure.Fuzz` was green the moment it compiled, which is expected — the solver is already correct on all of it. It was shown to bite by temporarily breaking `Structure.cpp` two ways (dropping the falling-support filter from the split: 4,604 failures from seed 20260754; stranding on un-orderability instead of on being one's own support: 4,025 failures from seed 20260742), then reverting. Do the same before trusting any future property added to it — one of the assertions written for it was measuring the wrong thing entirely, and only the mutation showed it.

**1 newton = 100 Unreal force units.** World scale is 1 uu = 1 cm, so force and impulse need a ×100 conversion while mass (kg) and density (g/cm³) need none. Strengths are stored in SI and converted at one named boundary. Full table in [DESIGN.md §3](DESIGN.md).

**The NaN guards and the shear cap are coupled — don't remove one.** `FMath::Min` is `(A <= B) ? A : B`, so `Min(NaN, cap)` returns the **cap**: a NaN shear capacity silently becomes a plausible number. The result still fails closed only because the compression axis is separately guarded by `IsFinite` and returns `Max()`, which then dominates. Drop that guard and the cap will launder NaN into a believable value.

  The related edge — a cap set *below* cohesion silently giving a joint less strength than its stated cohesion — is no longer untested at the **data** level: `Profiles.ConnectionInvariants` and `Profiles.MaterialInvariants` both sweep every row and reject a `MaxShearStrengthMPa` under its `ShearCohesionMPa`, so no profile in the library can be built that way. `ComputeUtilisation` itself still has no opinion on it, which is the right division of labour but worth knowing if a strength is ever constructed outside the library.

  **Dependents of that never-NaN guarantee**, so a refactor can find them: the shear cap in `ComputeUtilisation` itself, and the break comparison in `FConnection::ApplyForce` — the one line that decides whether a joint gives. The latter is written `!(x <= 1.0)` so it is locally correct even if the guarantee were ever broken; don't "simplify" it back to `x > 1.0`.

**`ComputeUtilisation`'s "always finite for any input" is slightly overstated.** A subnormal-but-positive capacity (e.g. `5e-324`) passes the `> 0.0` guard and yields `+Inf`. Unreachable from any real profile, and the break decision stays correct since `Inf > 1.0` — but a caller *summing* utilisations for a strain readout would get infinity. Tighten the wording or the guard when the readouts land.

**Degenerate inputs fail closed, and `FMath::Max` is why it matters.** `Max` is `(A >= B) ? A : B`, so every comparison against NaN is false and `Max3` *silently discards* a NaN — returning whichever other axis was lowest. A NaN load therefore produced a confident utilisation of **0.0**, meaning "unstressed, perfectly fine", which nothing downstream could detect. `ComputeUtilisation` now returns `TNumericLimits<double>::Max()` for a non-positive interface area or any non-finite stress. Guards are written `!(x > 0.0)` rather than `x <= 0.0` so a NaN is caught by the same branch instead of slipping past it. Locked down by `ConnectionStrength.DegenerateInputs`.

**A degenerate interface normal only fails closed inside `FConnection`.** `ClassifyForce` answers a zero-length or NaN normal with a *zero load*, which is right in isolation but reads downstream as "unloaded, perfectly healthy" — the fail-open hole appears only once the two halves are composed. `FConnection::ApplyForce` closes it by substituting a zero interface area, routing the case through `ComputeUtilisation`'s existing area guard rather than adding a second one. **Anything else that calls `ClassifyForce` and `ComputeUtilisation` directly re-opens the hole** and must make the same check (`FVector::Normalize()` returns false for both the zero-length and the NaN case, so one test covers both). Locked down by the bad-normal rows of `Connection.DegenerateInputs`.

## MVP: a wall you can watch break

The agreed next milestone. **Two bricks and one joint first** — visible, breakable, exercising the whole pipeline end to end — then scale to a wall, so later problems are wall logic rather than plumbing.

Architecture settled by spike (DESIGN.md §3): pieces are **kinematic while intact**, we compute connection loads ourselves, and a piece switches to dynamic when the connection holding it gives. **No Geometry Collections** — those are for pieces fracturing into smaller pieces, which the MVP does not need. That drops the heaviest dependency.

**`FStructurePiece` should take a material rather than a bare mass.** Materials now own density, so the brick actor (phase 3) can derive mass from dimensions instead of hand-setting it — but `FStructure::AddPiece` still takes a bare `MassKg`, so `StructureTest.cpp` keeps a literal `BrickMassKg = 2.72`. That literal is no longer unchecked (`Profiles.MaterialInvariants` derives the same mass from `ClayBrick`'s density and fails if the two drift), but it only goes away for real when a piece knows what it is made of. Small phase-3 change; do it with the brick actor.

**Fastener profiles assume a fastener density the data cannot express.** `Nail`, `Screw` and `Bolt` are EN 1995-1-1 characteristic capacities — a force per fastener, in kN — smeared over a reference of **one fastener per 100 cm² of interface**, because the model compares stresses and has no notion of how many nails are in a joint. The assumption is documented at the top of the fastener block in `ConnectionProfiles.cpp` and every figure scales with it. When fastener count becomes a property of a joint, these should be **re-derived from the kN figures, not re-tuned**.

**Deferred: connection-to-material pairing.** A joint's real strength depends on the pair, not just the connection — a nail holds far better in oak than in pine, and mortar bonds to porous brick but not to a sealed face. The answer is **not** an N×M×N table but weakest-link: a joint fails when *either* the connection gives, *or* the bond to a face peels, *or* the material itself fails, so effective strength is the minimum of those, with bond approximated as `connection_strength × material_bond_factor`. DESIGN.md §2 already gestures at this ("the mortar gives before the brick; the nail goes before the timber") without stating it as the rule. **Build it when a second material exists to prove it** — that is DESIGN.md §4's "add wood once, only to prove the code genuinely reads the profile". Written earlier, no test could tell it from a constant.

## The load solver — outstanding, and deliberately left alone

Everything here is known and unfixed. None of it blocks the list above.

- **`FConnection` is still copyable and the latch is still per-copy.** `for (FConnection C : Connections)` — a missing `&` — compiles clean, latches every overloaded joint *on the temporary*, and leaves the real connections untouched, so the structure reports zero broken joints under any load. `SolveAndBreak` holds by reference and `Structure.Cascade` reads every assertion back through `GetConnection`, so **the trap is closed at the one site that latches today** — but nothing in the type prevents the next one. Making it non-copyable was considered and rejected: no test drives it, it would break `AddConnection(const FConnection&)`'s value semantics and every fixture builder in the suite, and the actual defence is one ampersand. Revisit if a second site ever latches.
- **There is still no non-mutating way to evaluate a joint, and that is a finding rather than an omission.** `ApplyForce` is the only evaluator and it latches. The all-at-once policy does not need a `const` one — "break everything over capacity this pass" *is* evaluate-and-commit — so nothing was added. The moment anyone wants worst-first ordering, a live strain readout mid-solve, or a what-if trial distribution, it will be needed: a `const` "what would this utilisation be" alongside the committing call. Note the cascade tests already recompute utilisation externally via `ClassifyForce` + `ComputeUtilisation`, which is the shape that evaluator would take.
- **`CheckCascadeCase`'s `ReportedSupportedWeightUU` has a spec-vs-structure index desync one level up.** It indexes `Case.Spec.Pieces[Index]` while calling `Structure.IsPieceSupported(Index)` in the same loop. Safe today because no fixture specifies a piece that `AddPiece` rejects — but a row with a negative or NaN mass would shift structure indices off spec indices, and every per-piece assertion would then silently describe the *wrong piece* while still passing or failing plausibly. The connection-level version of this was fixed (the runner now walks `Structure.NumConnections()` and takes handles from `GetConnection`, which are validated at the door); this is the same bug one level up. Closing it needs a decision about what such a row should assert, so it is its own red test rather than a drive-by.
- **A degenerate fixture row must name the UNGROUNDED piece first, or it cannot reach the defect.** The harness bounds bug was originally reported with `{ 0, INDEX_NONE, ... }`, which passes green: `||` short-circuits, piece 0 is grounded, and the second handle is never evaluated. `{ 1, INDEX_NONE, ... }` is what actually reached it — `Array index out of bounds: -1`, process exit 3, the run aborted after 15 of 27 tests. Recorded so nobody re-derives a row that cannot fire.
- **`UtilisationTolerance`'s `1e-12` absolute floor is a constraint, not a taste.** The tolerance is relative `1e-9` with that floor, and the floor exists only for rows whose expectation is an exact zero. It must stay well below the smallest *non-zero* utilisation expectation in the file — currently `Unbreakable`'s 1.96e-11 — or that row stops being able to fail at all, which is what it was before (an absolute 1e-9 slack could not distinguish 1.96e-11 from zero, and zero is exactly what a joint dropped out of the load path reports). Noted beside the constant.
- **`GetBreakPass` and `HasGiven` can be made to disagree, through the front door.** `FConnection::ApplyForce` is public and the latch is a copyable member, so `FConnection C; C.ApplyForce(huge); Structure.AddConnection(C);` stores an **already-given** joint whose `ConnectionBreakPass` is `INDEX_NONE`. `GetBreakPass`'s contract says `INDEX_NONE` means "still intact", which is then a lie: the joint is invisible to the whole solver while `NumConnections()` still counts it. No caller does this today. The obvious near-term one is **save/load restoring a partly-collapsed structure**, and phase 5 replays exactly these stamps. Closing it is either a `GraphValidation` row (reject a connection that has already given) or a deliberate accept-and-stamp; either needs its own red test first.
- **A cycle in the support relation is reported, not solved.** Pieces caught in an unroutable knot — and only those; stranding is local, pinned by `Structure.StrandingIsLocal` and `Structure.StrandingPropagatesUpward` — are marked **unsupported**, so the stall is visible from outside and conservation holds. `Structure.SupportCycle` pins this, with a two-brick and a three-brick gap, plus two controls (a single grounded neighbour, and a cycle through a grounded piece that still resolves). What is still missing is any *rule for how load divides round a loop*: a course spanning a wide gap is reported as falling rather than as arching, which is physically the conservative answer but not the interesting one. Whoever wants real arching behaviour has to design that rule — see DESIGN.md §4's shear test, which is the scenario that will want it.
- **The fixpoint loop is load-bearing, and exactly one test says so.** `SolveLoads` iterates because stranding changes who reaches the ground, so a piece resting *only* on the knot must itself come out unsupported — and the pass that stranded the knot has already written that piece's weight onto its joint, because it is a leaf and Kahn seeds with it first. Only the re-solve wipes that. **`Structure.StrandingPropagatesUpward`** is what discriminates the loop from a single pass; delete the loop and its first case reports the brick supported with 2665.6 uu on a joint whose far end is falling. Don't "simplify" the loop away without checking that test still fails when you do.
- **The bed/head tier bakes in gravity as the only load direction.** "Substantially vertical" is `|normal.Z| > cos 45°`, which is meaningless once explosions and kinetic impacts arrive and the load no longer points down — routing has to generalise to the direction of the applied load. Flagged in DESIGN.md §3 as a known limitation of the model, not just of this code. The 45° line itself is pinned from both sides at 40° and 50° by `Structure.SupportTierThreshold`; the exact tie is deliberately unasserted, which is what makes `BedJointCosine` safe to spell as a `constexpr` literal — only a normal at *exactly* 45.000° could tell it from `1.0 / FMath::Sqrt(2.0)`. **The test file spells the same literal**, because `SpecSupportsOf` is the oracle for the `DegenerateInputs` matrix and has to agree with `RoleOf` bit for bit; change one and change the other.
- **A tilted joint ABOVE a piece supports it in tension, and that is accepted.** `RoleOf` tests `|NormalZTowardPiece| > cos45` before it looks at the sign, so the head tier is sign-blind: an inclined face over a piece is still that piece's fallback support, and holding it up means pulling the face open. Characterised by `Structure.TiltedJointClassification` — at 50° a 2.72 kg brick gives compression 0 / shear 2041.97 / **tension 1713.41**. DESIGN.md §3 states this outcome and accepts it, so **do not "fix" it**; it is why the 45° line looks like a cliff and is not one (just below it the same face is `BedAbove`, bears nothing, and the piece falls instead). Two comments in `StructureTest.cpp` used to read as properties of the *model* — "tension is always zero", "a gravity load path never pulls a joint open" — and are properties of the *fixtures*, every one of which is axis-aligned; both are now scoped, and adding a tilted normal to the `DegenerateInputs` matrix will turn its tension row red as a discovery rather than a regression. Note the design's "fails almost at once" is about the *ratio* of mortar's tensile to compressive limit, not about this load: one brick over 100 cm² reaches only 0.017 utilisation and breaks nothing.
- **Production's stranded set is not observable from outside, so the fuzz cannot compare it both ways.** `IsPieceSupported` cannot tell "in a knot" from "resting only on a knot" — both are correctly reported falling — so `Structure.Fuzz` compares the composite answer in both directions and the oracle's cycle set only one way (a piece on a cycle must be reported unsupported). Adding a seam to observe the stranded set is a production change and needs its own red test; the same seam would settle the pass-count item below. Not obviously worth it, but this is the gap if a future defect hides in it.
- **`SolveLoads`'s pass bound is provably 2, not `NumPieces + 1`, and nothing asserts it.** Stranding only removes nodes and edges, and removal cannot create a cycle, so a second pass can never strand anything the first did not — the third exists only to observe that and stop. Measured max across 8,500 fuzzed graphs up to 9 pieces: 2. Left unasserted because `SolveLoads` returns `void` and there is no seam to observe a pass count through; adding one is a production change and needs its own red test. Worth doing if the per-solve cost ever matters, since the bound is what multiplies the O(pieces × connections) figure below.
- **An unsupported island reports zero load on its internal joints.** Defensible for a static solver — nothing is holding it up, so there is no static load path — but it means "carries nothing" is ambiguous between *given*, *grounded on both sides* and *falling*. If a strain readout ever needs to tell those apart, it needs more than the force.
- **The solver is O(pieces x connections), and the knot check adds a walk per piece.** Building the support lists scans the whole connection array once per piece; replacing it with an adjacency index built once per solve is the obvious fix (it is outside the fixpoint loop, so it stays a single scan). Inside the loop, each pass redoes reachability, the load-path filter, the accumulation, and then `LoadReturnsToPiece` **once per supported ungrounded piece** — each a fresh walk with its own `TArray<bool>` visited buffer, so step five alone is O(pieces x (pieces + edges)). One Tarjan SCC pass would give the same answer in linear time, and a single reusable visited buffer would kill the allocations; both were left undone because nothing measures slow yet. A structure that strands nothing still pays for the walks. Fine at MVP size and deliberately not optimised; flag rather than fix until something measures slow.

  **This got more valuable with 2b, and was still deliberately not done there.** `SolveAndBreak` runs a *complete* `SolveLoads` per breaking pass, so the whole figure above is now multiplied by the number of joints that give — a collapsing wall re-scans the connection array once per piece, once per pass, once per break. The adjacency index remains the obvious fix and remains a pure performance refactor with no test driving it; doing it inside the cascade change would have mixed a behaviour change with a rewrite of the solver's internals.
- **`AddConnection`'s normal guard has a top-end hole.** A normal with components near 1e200 gives an infinite `SizeSquared`, `InvSqrt(inf)` is 0, so `FVector::Normalize()` returns **true** having produced the zero vector — and `RoleOf` then classifies that as a head joint, which is a support tier. Unreachable from real content, and left alone deliberately: closing it is branching logic, so it needs a red `GraphValidation` row (a huge-component normal, expected rejected) before the `IsFinite` check goes in.
- **`AddConnection` stores the interface normal exactly as given, non-unit included.** It only checks the normal *can* be normalised; `FConnection::ApplyForce` normalises its own copy each time it is called. Correct, and asserted by the "a non-unit interface normal" acceptance row, but it means the stored normal is not canonical — anything that compares normals directly must normalise first.
- **DESIGN.md §3's opening bullet still credits collapse to "Chaos strain-based damage".** That line predates the kinematic decision two subsections below it and the whole of `Core/Structure`; we compute the loads and decide the breaks ourselves, and Chaos only takes over the falling. Left as found because correcting it was not part of the change that noticed it. One-line fix whenever §3 is next opened.

## The graph representation — four assumptions that will break later

The structure is a graph: pieces are nodes, connections are edges, stored as a flat **edge list** (`Pieces` and `Connections` in `Structure.h`), with `PieceA`/`PieceB` as `int32` positions in the piece array. Adjacency is not stored — every `SolveLoads` derives three purpose-built adjacency structures over the **support relation** (`SupportConnections`, `Loaders`, `LoadPaths`), which is correct, because who supports whom changes as joints break and so cannot be cached on the pieces.

Four things are true today, load-bearing, and written down nowhere else. None blocks current work; each is cheap now and expensive later. Ordered by that ratio.

- **Piece handles are array indices, and nothing ever removes a piece.** Remove one and compact the array and every connection above it silently re-points at the wrong piece — no crash, no assert, just a structure that holds itself up wrong. Three planned features imply removal: debris that settles and despawns, the piece-size floor's mode 3 ("disappear"), and any culling of settled rubble. **2b sharpened this**: there are now *three* index-parallel arrays — `Connections`, `ConnectionForces` and `ConnectionBreakPass` — and the last is grown only by `AddConnection` and deliberately **never rebuilt**, because a pass stamp cannot be recomputed from anything. Re-point those and phase 5's playback shows the wrong joints failing in the wrong order, with `GetBreakPass` and `HasGiven` still agreeing perfectly. Fix before removal exists, not after: tombstone the slot and keep a free list, or move to generational handles.
- **The solver is global, but collapse is local.** One `SolveLoads` walks every piece. Break a wall in half and the two independent structures stay in one array and are re-solved together — and `SolveAndBreak` now does that once per breaking pass, so knocking one brick out of a building re-solves the whole building, repeatedly. The answer is connected-component islands solved independently plus dirty-region tracking, so only the component that changed re-solves. The current shape neither resists nor helps this. Expect it to be the first of the four to actually hurt.
- **Pieces have no position, and force delivery is inherently spatial.** "A piece is a mass and an identity" is why the maths is fast, deterministic and testable without a world, and it should stay that way. But it means the solver can never answer *which pieces are near this point* — and explosions with radial falloff and kinetic impacts, both open threads in DESIGN.md §6, start exactly there. Something above the solver must own geometry and hand down piece handles. That boundary is undesigned and is the natural next design conversation.
- **Connections are only ever destroyed, never created at runtime.** Breaking is monotonic. Real collapse does the opposite too — debris piles up and a fallen slab comes to rest on something and starts carrying load. Under this model rubble can never support anything. Fine for the MVP and for a good while after, but it needs contact detection, so it lands on top of the item above.

One smaller live footgun: connections are stored undirected, but **the force sign depends on which end is `PieceA`** (`Structure.cpp`'s accumulation, and `ConnectionLoad.h`'s convention that the force belongs to `PieceB`). Anything that ever rebuilds, sorts or deduplicates the connection array must preserve that orientation, or compression silently becomes tension.

## Core systems — designed, not built

DESIGN.md §2–3 specifies all of it.

**`FConnectionStrength` is a plain C++ struct, not a data asset.** DESIGN.md §2 calls for a data asset and for materials to be "data, not code". Half of that is now true — `Core/Profiles` makes adding a material or a connection type **adding a row**, with no new class and no new branch — but it is still a row in a `.cpp`, so it needs a recompile and there is no `USTRUCT`, no `UPROPERTY`, nothing tunable in the editor. Correctly deferred rather than speculatively built; this is the remaining gap between the current shape and the stated design.

**Shear direction is discarded.** `FConnectionLoad::Shear` is a magnitude only. Fine for isotropic materials, but DESIGN.md notes wood fails by splintering *along the grain* — grain-relative shear direction will matter once anisotropic materials arrive. Revisit then; don't add it speculatively.

**Base destructible actor** wrapping a Chaos Geometry Collection, with damage threshold and connection strength, exposing apply-damage-at-location. Needs a live world and a ticking solver, so expect integration-shaped tests rather than unit tests.

**Material profile data asset** — density and directional strengths now exist in `Core/Profiles/MaterialProfiles`; **fracture pattern** does not, and neither does anything authorable in the editor (the data-asset gap noted above).

**Connection types as data profiles** — mortar, nail, screw, bolt all exist in `Core/Profiles/ConnectionProfiles`, and `Core/Connection` takes an `FConnectionStrength` whole. What is missing is the **in-game builder choosing between them**, and the data-asset gap noted above.

**A second, dissimilar material — wood — added exactly once.** DESIGN.md §4: don't write a test per material; add wood one time only, to prove the directional code genuinely reads the profile rather than having brick's numbers baked in, by running the same shear scenario on it and confirming it survives where brick failed. **Deliberately not added with the profile library** — adding it alongside the calibration data would spend that proof for nothing. Goes together with the connection-to-material pairing rule that `BondFactor` is reserved for.

**Damage / force manager** — routes hits, explosions, radial forces to the right actors.

**Piece-size floor + three modes.** Build modes 1 (indestructible) and 3 (disappear) first — they prove threshold detection simply. Mode 2 (Niagara dust) after.

**Piece creation timestamps** — stamped when a piece breaks free, inspectable live, used to recover failure sequence.

**Scenario base class + tiny default scenario.** DESIGN.md §5: the scaffold spawns a *scenario* and knows nothing about bricks. Brick wall is one scenario. Also needs the in-world overlay menu (scenario switcher + strain readouts) — the game should never be an empty void.
